# 训练 RSI 协议

**来源层级** · 来自模型训练适配与跑通、以及运行后消融实验的实战经验。本流程适用于不同模型；各项因素的影响大小，应在当前工作负载上实际测量。

## 性能驱动的优化

当任务优先关注端到端训练性能时，使用 [MFU Riser 性能策略](../../mfu-riser/references/contracts.md#performance-policy)，并声明筛选门禁和验收门禁。

- 根据实际使用的模型架构和真实序列长度审核模型 FLOPs。当简化的 PaLM 估算与参考计算的差异处于声明的容差内时，可以使用该估算。报告中应包含计算口径、MFU、HFU 证据覆盖范围、每设备有效 tokens/s，以及优化成本。参见[利用率口径](mfu-targets.md)。
- 当基线较低时，先核实测量，再量化与目标的差距。使用 [MFU Riser 规划指南](../../mfu-riser/references/planner.md)对关键路径上暴露的瓶颈排序，并考虑等价模块替换、算子融合、通信调度和并行布局调整。诸如 10% 的阈值，应作为特定任务触发该调查的条件。
- 优先考虑框架执行、流水线调度、兼容的高性能模块或内核复用，以及计算与通信重叠。当当前工作负载的证据表明这些方向的收益进入平台期时，再深入硬件计数器和自定义内核调优；不要以 MFU 跨过某个通用阈值作为升级调查层次的依据。遵循[分层性能诊断](hierarchical-performance-diagnosis.md)。
- 保持模型深度、宽度、专家数量、逻辑 Top-K、要求完成的 token 工作量及训练语义。在此范围内调节并行布局、激活生命周期、预取和优化器实现等执行设置。可调执行设置放入候选源码或配置，固定任务约束放入工作负载定义。
- 如果任务允许调整序列长度、batch 或梯度累积，为每个选定工作负载测量一个[关联容量实验系列](../../mfu-riser/references/contracts.md#linked-series)。检查支持的长度、峰值显存和梯度归一化，并延续任务的容量要求。只有任务明确要求时，才将基线规划时预留的显存视为约束。

出现实质性的正确性或性能缺陷时，遵循[故障修复流程](failure-repair.md)。保留原始失败工作负载，定位并修复原因，然后在不带诊断探针的情况下重跑。缩小工作负载或禁用执行路径属于诊断手段，不能作为缺陷已修复的证据。跨布局数值比较前，验证逻辑初始化状态一致；审核每一个参与累积的 microbatch，而不只是优化器更新。

## 固定实验条件

- 将第一个通过验证的独立适配版本固定为 B2。已接受的优化版本 A 保持在其版本演进链上，并记录父提交和候选提交。如果存在独立参考 B1，分别声明相对 B2 的改进目标，以及达到 B1 水平的性能目标。固定预算，并在运行结束时分别报告结果及剩余差距。
- 比较前固定工作负载、硬件、路由、计时所用的插桩、指标公式、单设备峰值算力、预热和测量窗口。启动前立即检查进程和设备占用，结束后确认资源释放。若存在资源争用，则受影响的测量无效。
- 盲测运行的可读输入中，不得包含参考实现、已解析的 Recipe 或既有解决方案。在揭盲前，对固定的最终版本评分。后续消融实验单独记录为诊断。

## 分离正确性与性能测量

对同一个已提交候选运行两个窗口。正确性窗口包含必要的输入哈希、标量检查和张量探针；性能窗口则保证候选与基线使用一致的插桩。优先使用轻量标记验证预期执行路径确实生效。验证开销会影响判断时，应单独测量。

如果输入指纹计算占据主要验证时间，分别测量其传输和序列化开销。对于纯数据并行，Trainer 的 [InputIdentityRecorder](../../../../hyper_parallel/tools/model_integration/tensor_probes.py) 在字段所属 rank 上计算字段值的哈希，并交换各组成部分的摘要。沿上下文维度分片的字段仍保留逻辑张量重建流程。引入记录器优化时，要验证预期的 rank 和 microbatch 覆盖范围，并比较完整指纹与数值轨迹。

除了请求的配置，还要固定实际生效的原生执行模式：扩展与算子包摘要、归约确定性和执行计划选择覆盖项，都可能在模型提交不变的情况下改变算术执行路径。如果正确性与性能使用不同模式，必须声明并验证两者；参见[原生分发的可重复性](failure-repair.md#verify-repeatability-through-native-dispatch)。

在运行候选前选择门禁：

| 修改类型 | 正确性证据 |
|---|---|
| 调度或等价实现 | 一致的输入，以及声明的数值等价性门禁 |
| 融合内核或不同精度的内核 | 局部一致性验证，以及按照预先声明容差执行的完整模型检查 |
| 优化器、路由、数据语义等训练策略 | 单独获得批准的训练质量验证协议，使用一致的评估输入和预算 |

固定专家路由应视为性能诊断手段。训练质量验收使用原生路由。改变路由、数据或插桩策略的 benchmark，应建立独立的比较系列。

## 结构化训练执行凭据

初始化新的 autoresearch 运行目录后，将以下协议加入 `run.json`，并将 `gate_cmd` 和 `benchmark_cmd` 分别设置为独立的 argv 列表。

```json
{
  "training_protocol": {
    "workload_id": "sha256:replace-with-workload-digest",
    "gate_steps": 30,
    "benchmark_steps": 30
  }
}
```

根据固定的数据、形状、硬件、拓扑，以及两个阶段声明的路由与测量设置，生成实验系列 ID。每个包装脚本在启动前检查实际解析出的阶段设置是否与声明一致，并报告该系列 ID。记录基线时，门禁检查基线自身的一致性；后续迭代则检查候选的正确性。

每个阶段的步数包含预热，并以已完成的优化器更新次数计数。短筛选应单独进行。候选只有通过完整门禁和 benchmark 后，才能进入保留版本的演进轨迹。验收时对固定的最终候选进行独立复测，并将这些测量与候选选择时的测量分开记录。

包装脚本应在结尾输出且只输出一条凭据行，由 `RSI_TRAINING_RECEIPT`、一个空格和一个 JSON 对象组成。失败时，只要能够报告，也应输出该行。

```text
RSI_TRAINING_RECEIPT {"workload_id":"sha256:replace-with-workload-digest","phase":"gate","status":"numerical_mismatch","completed_steps":17,"engaged":true,"first_error_step":18}
```

- `phase` 为 `gate` 或 `benchmark`。`engaged` 应根据预期路径实际运行的证据设置。成功调用应报告 `passed`、与计划完全一致的完成步数、路径生效状态为真，并以退出码零结束。benchmark 还应输出其正常的指标行。
- 已知的终止失败使用 `oom`、`numerical_mismatch`、`incomplete`、`cleanup_failed`、`contention`、`futile` 或 `error`。观察到相应信息时，包含 `first_error_step` 和 `allocation_retries`。
- 无效进展监控器（futility watcher）在向进程组发送信号前检查进度。窗口完成后，应让包装脚本完成证据采集和资源释放。清理失败应与窗口未完成分别记录。若 `futile` 凭据的完成步数达到或超过最后一步，则该凭据会被拒绝。

循环在 `candidates.jsonl` 中记录基线及后续候选的任务耗时、退出码、窗口完成情况和失败类别。开始迭代前必须有通过的基线；实验系列的协议会被固定；噪声确认重跑也执行相同的凭据检查。旧版运行目录可以继续使用已有的标记协议。

## 在迭代之间传递证据

将[验收经验沉淀](acceptance-learning.md)视为每个 RSI 任务的必需交付物，不要等待用户再次提出要求。使用[自动沉淀流程](../../autoresearch/references/experience-consolidation.md)：默认在验收时集中沉淀；用户选择时，也可持续沉淀。复盘所有结果，而不只是保留的改进。区分操作规程和已经实现的实验框架检查，不要把未经验证的建议提升为经过测量验证的指导。

- 记录实际运行路径、最早失败的阶段或步骤、断言或错误，以及门禁窗口和性能窗口。如果某个算子通过了局部一致性检查，却在读取卸载状态时失败，应先将观测逻辑与训练路径隔离，再重新评估算子。
- 在 [autoresearch 台账](../../autoresearch/SKILL.md#candidate-receipts-and-retries)中保留暂缓候选及其依赖范围。预取在慢配置上的收益可能处于噪声范围内，但在计算或优化器改变后变得可测。当声明的依赖范围有改动被保留时，以新的父版本为基准重新测量该候选。
- 当两个修改可能相互影响时，从同一个父版本分别测量两者，再测量其组合。分别报告单项修改的差值与累计对齐后的差值。每个候选都必须保留正确性和路径生效门禁。
